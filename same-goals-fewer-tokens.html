The six patterns behind the spend

  1. The everything-doc run. One session, one work document, iterate until done. (Spender #1 — see the debate in §3.)
  2. The repeated verification question. "Has X been implemented?" asked fresh each time, each ask re-reading the whole repo. (Spender #3.)
  3. Big-bang planning in a live session. Detailed plans + parallel agent teams in the same context that then executes. (Spenders #4, #8.)
  4. Whole-project port. Rust rewrites of working tools. (Spender #5, plus the review-tool clone at 48M.)
  5. Vague continuation in a long session. "continue refresh" — no done condition, no scope, session runs until something stops it. (Spender #6.)
  6. Mechanical tasks in bloated sessions. README, branch rename. The work cost nothing; the context cost everything.

3 · Long orchestrator runs: two pits, one verdict

The orchestrator run is the most expensive thing you have done in Claude Code — and it is also the most work you have gotten out of a single session: multiple epics, implemented and reviewed, across 94 hours with 181 subagent transcripts. Pretending it was simply a mistake throws away the reason you built it. So the two positions, argued against each other from your own data:

Pit #1 — "It was worth it. Make it cheaper, don't kill it."

The run produced reviewed implementations for an entire work document in one launch. The cost was not the orchestration pattern — subagents are exactly how you keep the main context small — the cost was that nothing bounded it:

  • Main thread ran 1,735 turns on glm-5.3 with median context 522K against a 250K compact window. The orchestrator prompt even said "your own context stays small." It didn't, and nothing enforced it.
  • The run predates the guards: usage-guard.py was verified 2026-09-13, two days after this run ended. The guide's runaway replay showed the same session at 6.8x cheaper with a compact window plus tier split.
  • Split per epic, each orchestrator starts with a fresh, small context; cross-epic state lives in checkpoint files on disk — the plan/history machinery you already have — not in a 500K-token conversation.

The fix is fencing, not abolition: per-epic sessions, Flash for implementation subagents, deep tier only for reviews, CLAUDE_BUDGET_ZAI_HARD as a hard ceiling, and the peak-hours guard on anything left unattended.

Pit #3 — "At 2B tokens, the pattern is too expensive at any price."

The numbers say the orchestrator's core promise failed. "Your own context stays small" was the design's first principle, and the main thread burned 900M tokens anyway — 96% of it cache re-reads of its own accumulated context. Why this predicts every future run fails the same way:

  • An orchestrator's job is to hold state for everything — item briefs, specs, review verdicts, teammate messages. That state only grows. 454 "user prompts" were injected into this session, most of them teammate notifications the orchestrator must read. The context cannot stay small by construction, and no prompt will make it.
  • Unattended + deep tier + no ceiling is the guide's one hard rule, violated for 94 hours. The next run will violate it again, because the incentive at launch ("just let it finish") is exactly the incentive that created this one.
  • Per-epic sessions don't lose much: epics in the doc are mostly independent, and each epic's subagents start fresh regardless. The cross-epic context the mega-session preserved is the same context that cost 522K per turn to re-read.

The pattern's failure mode is not incidental — it is the design. Delete it, work the doc one epic per plain session, review each with a fresh deep-tier pass.

Verdict: fence it, and make the fence load-bearing

Pit #1 is right that the work was real; Pit #3 is right that the pattern as-run cannot be repeated. The resolution is to keep the orchestrator but bind it to the things it refused to do for itself:

  1. Scope = one epic. The generated prompt says "tackle all of the work in that document." Change it to one epic per launch, with the next epic as a fresh session reading the checkpoint file. This is the single biggest lever: it caps the context the 96.3% tax applies to.
  2. Tier split the subagents. Implementation subagents on Flash; only the review pass on GLM-5.3. Reviews are the judgment calls; implementation from a tight spec is typing.
  3. State on disk, never in context. Item status, briefs, verdicts go to a checkpoint file after every task. The orchestrator reads the file, not its own history.
  4. Launch fenced or not at all: CLAUDE_BUDGET_ZAI_HARD=15000 ZCLAUDE_PEAK_POLICY=enforce on every unattended run. If a legitimate run needs more, raise it consciously at launch, not after the fact.

Rough arithmetic, assumptions stated: main-thread cost scales roughly with median context × turns. Capping median context at ~250K (compact window actually firing) halves the 900M main-thread share; per-epic sessions cap it further because most turns run well under the ceiling. Flash implementation subagents at roughly a quarter of GLM-5.3's rate cut most of the 1.19B subagent share. Combined, the same work plausibly lands in the 400–700M range — not the guide's 6.8x, because this run's output volume was real, and reviews stay on the deep tier. Anyone quoting you a 10x saving on this run is selling something.

4 · Prompt rewrites

Each rewrite follows the guide's §6 shape: explicit path, done condition, scope boundary, escape hatch. Same goal, bounded blast radius.

4.1 The everything-doc run

Create a prompt I can use that will tackle all of the work in that document iteratively with a QA pass after each task…

The generated prompt then ran until the document was empty. Rewrite the generated prompt itself:

Work through @docs/product-blind-spots-2026-09-07.md, Epic 6 only ("Campfire chat + Pings"). Done condition: every task in Epic 6 implemented, reviewed by a subagent review pass, tests green, checkpoint file updated, work committed. Rules: - Read the checkpoint file at docs/blind-spots-state.md first. It holds completed-item status and design briefs — trust it over your own memory. Update it after every task. - Dispatch implementation subagents; brief each with only what that task needs. - Your own context: if the conversation exceeds the compact window, finish the current task, update the checkpoint file, and stop. I will launch the next session. - Scope: do not start Epic 7. Do not refactor code outside the epic's files. - If a task needs a judgment call the spec does not answer, stop and print ESCALATE: <question>. Do not guess. Launch with: CLAUDE_BUDGET_ZAI_HARD=15000 ZCLAUDE_PEAK_POLICY=enforce zclaude deep --danger -p "$(cat epic6-run.md)"

What changed: the unit of work shrank from "the document" to one epic; the checkpoint file, not the conversation, is the state; the budget and peak guards are attached at launch; and the escape hatch replaces silent guessing. Run six of these instead of one, and each one is killable.

4.2 The repeated verification question

Has everything in @docs/critical-review-2026-02-21.md been addressed?

Asked three times in three sessions ≈ 135M tokens, because each ask re-read the doc, the repo, and the git history to rebuild the same answer. Two fixes — one-time setup, then a cheap recurring prompt:

Once, in a fresh session, have the review written down as a persistent checklist:

Read @docs/critical-review-2026-02-21.md. For each finding, add a row to docs/review-state.md: finding ID, one-line summary, status (open | fixed | wontfix), evidence (file:line or commit SHA). Do not fix anything. Done condition: every finding in the doc has a row.

Then every future "has it been addressed?" becomes incremental:

Verify open items 12–40 in docs/review-state.md against the current code. For each: flip status to fixed with evidence, or leave open with a one-line reason. Update only that file. Do not re-read findings already marked fixed. Done condition: no item in 12–40 left unverified.

Each run touches one file plus the code for the open items — tens of thousands of tokens, not tens of millions. This is also exactly what a slash command is for: the template stops being fresh tokens each time (guide §6).

4.3 Big-bang planning in a live session

Create a thorough, detailed plan to implement all improvements from @CRITICAL-REVIEW.md using parallel agent teams.

The plan is a judgment call — deep tier, correct. The mistake is doing it in the session that then executes, so the whole plan lives in context for the rest of the work. Split by artifact:

Read @CRITICAL-REVIEW.md and write a phased implementation plan to docs/impl-plan.md. One phase per coherent chunk, each phase listing: files touched, done condition, verification steps. Use the plan format from my plan/history setup. Do not implement anything. Ask me clarifying questions before writing if scope is ambiguous.

Then execution is per-phase fresh sessions — you already have /sym-phase and the phased-project template for exactly this. Each session reads one phase (~a few thousand tokens), not the planning conversation (~hundreds of thousands).

4.4 The whole-project port

I want to create a Rust version of this project. Create the local repo as a sibling to this project, then create a detailed plan. Ask me clarifying questions. Do not make any changes to this repo.

Honest assessment: this is already a good prompt — explicit location, clarifying-questions gate, scope boundary. Its 119M came from doing the survey of the entire source project in an interactive session. The upgrade is directional, not structural:

Port this project to Rust as a sibling repo at ../screencap-rs. First: inventory the source. For each module record, in PORT-PLAN.md: what it does, its public interface, test coverage, and a port difficulty score. Do not read implementation bodies of modules scored "trivial" — interface + tests are enough to port them. Then plan the port in phases in PORT-PLAN.md and stop for my review before writing any Rust. Do not modify anything in the source repo.

"Interface + tests are enough" is the line that matters: it stops the session from ingesting every implementation body, which is where the tokens went. Same pattern for the review-tool clone.

4.5 Vague continuation

continue refresh

108M tokens, no done condition, no scope. Continuation prompts are fine mid-task; they are expensive when they are the only instruction for hours. Same task, bounded:

Continue the refresh skill run. Done condition for this session: refresh cycle completes for all sources in config/sources.yaml, failures logged to refresh-errors.log, summary printed. If any source fails twice, skip it, log it, keep going. Stop and report when done — do not start a second cycle.

4.6 Mechanical tasks in bloated sessions

Rename the master branch to main, then push.

44M tokens for two commands, because the session carried 40M tokens of prior context. The rewrite is not better wording — it is a fresh session (/clear, or /rewind if the bloat is recent):

(new session) In /Users/you/projects/screencap-rs: rename branch master to main, update the remote, push with -u. Report the tracking branch when done.

Rule of thumb from your own data: if a prompt takes under one line and the task has no judgment in it, it belongs in a fresh session (or a shell), not in the conversation you happen to have open. Same for "Create a README.md" at 105M — fine prompt, wrong session; a fresh one with "read only code and existing docs in repo root and src/, do not read tests or vendored code" would have cut it by an order of magnitude.
